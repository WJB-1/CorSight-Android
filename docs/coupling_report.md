> 调研日期: 2026-06-14

---

## 一、全局概览

| 指标 | 数值 |
|------|------|
| 扫描文件数 | 15 |

---

## 二、耦合度评估矩阵

| 模块 | 耦合度 | 说明 |
|------|--------|------|
| 菜单数据配置 | **高** | 菜单项列表、颜色、标签全部硬编码在 `MainActivity.setupRingMenu()` |
| 菜单动作执行 | **高** | `executeRingMenuItem()` 的 when 分支直接调 Activity 内部方法 |
| MenuAction 类型扩展 | **高** | sealed class 要求改源码才能新增动作类型 |
| 菜单绘制样式 | **中** | RingMenuView 的 Paint 颜色、尺寸比例全部内部常量 |
| 手势检测 | **低-中** | GestureCallback 接口抽象良好，但单例模式 + 硬编码阈值限制灵活性 |
| 语音命令解析 | **低** | VoiceCommandInterpreter 纯逻辑类，但 113 个关键词硬编码在源码中 |
| 语音命令执行 | **高** | CommandExecutor 实现直接依赖 Activity 成员变量和 UI 组件 |
| 动画系统 | **不存在** | 所有视觉变化是 visibility 硬切换，无动画抽象层 |
| 网络层 | **中** | URL 散落各文件，明文 IP 暴露 |

## 九、结论

当前代码的主要耦合问题集中在 **MainActivity 这个 God Activity** 上——它实现了 5 个接口、持有 12+ 个依赖、承担了地图/导航/语音/菜单/搜索/历史/设置 7 大职责。

**硬编码问题**方面，300 处中文字符串是最突出的问题，但优先级不如安全问题（明文 IP）和架构问题（菜单/命令解耦）。

**解耦的第一步**应该是：把 `CommandExecutor` 的实现从 MainActivity 中抽出来，放到一个独立的 `AppCommandHandler` 类中——这一改动能让语音命令、环形菜单、手势检测三者共享同一套命令执行逻辑，消除当前的重复实现。
